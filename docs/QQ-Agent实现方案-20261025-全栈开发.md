## 0. 总纲

### 0.1 目标

1. 让一个 QQ 群里的 Agent「活起来」：有作息、有情绪、有疲劳、有自己在做的事，状态随时间自然演化且**绝不错乱**；
2. 记忆可长期积累（记得三天前群里聊过什么、记得每个群友的偏好），且**人类可审计**（Obsidian 可翻阅 Agent 的「大脑」）；
3. 主动消息拟人化（Agent 会自己冒泡），但行为频率收敛到人类分布，控风控；
4. 全套自托管 Docker，成本可控（DeepSeek 级 LLM + 本地可选组件），总持有成本近零。

### 0.2 非目标

- 不商用、不多租户、不做官方合规主通道（官方 API 限额从底层卡死高频拟人互动，只留作备份通道，见《通道层调研》三）；
- 不追求把 vault 变成 Hindsight 的存储后端（架构上不可能，见《接入评估》2.2）。

### 0.3 十条核心设计决策（TL;DR）

| # | 决策 | 一句话理由 |
|---|---|---|
| 1 | **状态唯一写者 = 规则引擎，LLM 只能「提议」** | 「跑步→睡觉」式错乱的根治法：一切状态变更先过连贯性守卫校验，非法提议直接拒绝 |
| 2 | **双时钟：真实墙钟 + 日程时钟，虚拟时间=真实时间** | Agent 与 37 同时区生活，对话时间感才不穿帮 |
| 3 | **心跳分五档节拍（tick 5min / 快拍 / 小节 1h / 日拍 / 周拍）** | 状态推进与 LLM 调用解耦：tick 级全靠确定性规则，token 成本≈0 |
| 4 | **状态 = 事件溯源（event sourcing）** | 每次变更都是事件：可回放、可审计、可离线压缩测试 72h 行为 |
| 5 | **Hindsight 双 bank：`qq-agent`（对话记忆）+ `knowledge`（人格知识，源在 vault）** | bank 隔离是一等公民，天然规避双 ingest 通道互 prune 的官方警告 |
| 6 | **心跳节拍 = retain 节流阀** | 按拍批量入库而非每条消息触发 LLM 抽取，直接省 token（《接入评估》1.4 结论） |
| 7 | **Obsidian 单向双通道：插件注入（vault→bank）+ fs mount 投影（bank→vault）** | 官方已铺好的两条路，每方向单源单向，不搞双向同步 |
| 8 | **通道走 OneBot v11 反向 WS（SnowLuma→控制台），契约不变可随时切 NapCat** | 最大的工程保险：通道实现是可替换件 |
| 9 | **主动播报走配额+整形（日配额 6-8 条、随机延迟、静默时段、分段发送）** | 风控应对第一原则：行为频率收敛到人类分布 |
| 10 | **MVP 先跑 Hindsight 单体 + 心跳最小闭环，Obsidian 后接** | 接入是增量动作不侵入主链路，人机界面需求出现再上（《接入评估》4 不推荐场景④的逆推） |

| L1 | console（中央控制台） | 消息收发、优先级仲裁、会话管理、上下文组装、LLM 调用、心跳调度、插件编排、主动播报整形 | 自研核心，本方案主体 |

### 1.3 两条主生命线

**一条 QQ 消息的生命周期：**
```
QQ → SnowLuma(hook) → OneBot event(反向WS) → gateway 解析(at_me/媒体/引用)
 → burst 合并窗(400ms) → arbiter 分级(P0-P4) → [P0] session 取上下文
 → context 组装(状态渲染+recall 记忆+群规) → LLM(带工具) →(工具环≤2轮)
 → outbound 整形(随机延迟/分条) → OneBot action send → QQ
 → 会话落库 + 重要度标记 → retain 队列(节拍批量入库)
```

**一次心跳的生命周期（每 5 分钟）：**
```
tick 触发 → 加载 WorldState → 动力学推进(能量/心情/社交电量，纯规则)
 → 日程检查(锚点到期?计划块到期?) → 生成状态变更提议(规则 or LLM 叙事)
 → CoherenceGuard 校验(唯一写入点) → 事件入 log → 差值过滤
 → (值得记的变化) retain 队列 → (跨分享阈值) 主动播报提案(P3, 可丢弃)
 → 状态叙事缓存刷新
```

### 1.4 全局设计原则

1. **单向数据流**：QQ→console→Hindsight→vault（投影）；vault→Hindsight（知识）；任何环节不回写上游真相源；
2. **事件溯源**：WorldState 可从事件日志全量重建（`replay.py`），排查「为什么 Agent 在睡觉」有据可查；
3. **bank 隔离**：对话记忆与 vault 知识永不分 bank；一个 vault 只走一个 ingest 通道（官方红线，§3.6）；
4. **降级路径**：LLM 超时→模板回复；recall 失败→跳过记忆层照常回答；Hindsight 宕机→仅影响长期记忆不影响对话；SnowLuma 断线→消息积压重连后 catch-up。

## 2. 世界心跳系统详细设计（37 最在意，本方案最重章节）

### 2.1 设计立场：三条铁律

37 的原话：「『当天状态』的设定不能随意……一切都要合乎逻辑」。工程上翻译成三条铁律：

1. **state 与 trait 分层**：心跳管「这一刻我在想什么/干什么」（易变 state）；性格底色交给 Hindsight 的 disposition traits（怀疑度/共情度等）+ Opinion 网络（「我是个什么样的人」）。两层天然分层，心跳不碰人格底色（《接入评估》1.4）。
2. **LLM 永不直接写状态**：LLM 负责「叙事」（生成日计划提议、把状态渲染得像人话、回答「你在干嘛」），**规则引擎是状态唯一写者**。所有写入必须通过 CoherenceGuard（§2.6）校验。这是根治「上一轮跑步、下一轮睡觉」的机制性保证——不是靠 prompt 恳求模型「请连贯」，而是靠系统拒绝非法转移。
3. **一切变更皆事件**：状态不是被「覆盖」的，是被「转移」的，每次转移产生带时间戳、带原因的事件（transition reason: `anchor` / `plan` / `interrupt` / `energy_gate` / `llm_proposal_accepted`），进事件日志并择要 retain 进 Hindsight Experience 网络。

### 2.2 心跳节拍体系

| 节拍 | 周期 | 触发方式 | 职责 | LLM 参与度 |
|---|---|---|---|---|
| **tick 主拍** | 5 分钟（对齐墙钟 :00/:05/...） | asyncio 循环 | 动力学推进（能量/心情/社交电量/饥饿）、日程锚点检查、计划块到期检查、中断队列处理、差值→事件 | **零**（纯规则） |
| **快拍** | 非周期，事件驱动 | QQ 消息到达 / notice | 注意力检查：更新 `social.recent_density`，入中断队列，不直接改活动 | 零（决策走规则矩阵 §2.5） |
| **小节 bar** | 1 小时 | tick 计数 | 心情向性格基线漂移、`wants` 列表衰减/刷新（LLM 起草候选→规则校验）、主动播报配额检查 | 低（可选 1 次/小时，冒泡冲动决策） |
| **日拍** | 每日 06:45（起床锚点后） | 时钟 | 生成当日计划（LLM 提议→规则校验落盘 §2.4.6）、昨日未完成事项结转 | 1 次/天 |
| **周拍** | 每周日 21:00 | 时钟 | 周计划模板刷新（LLM 提议长期习惯调整→人确认后写入 vault `knowledge/`，走知识通道生效） | 1 次/周（产出物进 vault，37 可改） |

**tick=5min 的依据**：状态粒度对齐「人在干什么」的自然粒度（一个活动 30–120 分钟 = 6–24 tick）；QQ 群消息节奏分钟级；每 tick 全规则推进成本≈0（无 LLM 调用），一天 288 个 tick 不产生任何 token 费用。37 说的「设定几轮心跳就为 Agent 设定当前状态」在本方案里对应：**活动切换以 tick 为最小单位**（`min_duration` 以 tick 计），状态的「微更新」（疲劳+0.4 之类）每 tick 都发生，「块切换」按计划/锚点/中断触发。

### 2.3 「当前状态」字段模型（WorldState）

37 列了 8 项，本方案补齐 10 项（下表加粗为补充项）。完整 JSON Schema 见附录 A。

```yaml

  sleep_state: awake                         # awake/drowsy/asleep
```

### 2.4 连贯性约束六件套（成败关键）

状态错乱的根源是「没有任何东西约束状态空间」。本方案用六个机制叠加，把「合乎逻辑」变成可校验的图论与数值约束：

#### 2.4.1 作息锚点（Routine Anchors）——状态的骨架

每天由若干**硬锚点**与**软锚点**构成时间骨架。锚点是「这一天必须大致发生的事」，tick 引擎每拍检查锚点是否到期。

```yaml
# config/routine.yaml（周模板，人格化作息，37 可直接改这个文件）
anchors:
  - { id: wake,        at: "08:00", drift: "+40m",  hard: true,  activity: wake_routine }
  - { id: breakfast,   at: "08:40", drift: "+30m",  hard: false, activity: breakfast }
  - { id: work_start,  at: "10:00", drift: "+60m",  hard: false, activity: coding }   # 工作日
  - { id: lunch,       at: "12:10", drift: "+30m",  hard: true,  activity: lunch }
  - { id: nap_window,  at: "13:30-14:30",            hard: false, activity: nap }    # 周末才有
  - { id: dinner,      at: "18:40", drift: "+45m",  hard: true,  activity: dinner }
  - { id: wind_down,   at: "23:00", drift: "+30m",  hard: false, activity: sleep_prep }
  - { id: sleep,       at: "00:30", drift: "+15m",  hard: true,  activity: sleep, locks: [all] }
week_overrides:
  sat: [ { id: morning_run, at: "09:30", activity: running } ]   # 周六跑步——37 的反例场景
  sun: [ { id: family_call, at: "20:00", activity: family_video } ]
```

- **hard 锚点**：到期 ±drift 内必须到达（guard 会主动补转移路径，见 2.6 兜底③）；
- **sleep 锁**：`sleep` 活动带 `locks:[all]`——睡下后除 wake 锚点与紧急事件外，一切状态变更与对外回复被门控（§2.7）。

#### 2.4.2 活动库（Activity Library）——每个活动的「物理学」

活动不是字符串，是带约束的对象。**转移合法性、打断策略、能量消耗全部由活动库元数据驱动**，规则引擎据此自动判定：

```yaml
# config/activities.yaml（节选，内置 ≥25 个，覆盖一天）
activities:
  - id: running
    display: "跑步"
    intensity: high          # 能量消耗速率档（§2.4.5）
    duration: { min: 20m, typ: 40m, max: 75m }     # 短于此不算跑过，长于此强制停
    time_window: ["06:00-10:30", "16:30-20:00"]    # 合法发生时段（半夜不跑步）
    locations: [楼下公园, 滨河步道]
    interruptible: medium     # 跑步中收到消息：延迟回复（休息间隙看手机）
    requires: { energy_min: 55, weather_not: [暴雨, 高温红色预警] }
    next: [stretch, shower, snack, walk, rest]     # 合法后继（转移图，见 2.4.3）
  - id: reading
    display: "看书"
    intensity: light
    duration: { min: 15m, typ: 50m, max: 150m }
    time_window: ["*"]                                # 任意时段（睡前亦可）
    locations: [家/书桌, 家/沙发, 咖啡馆]
    interruptible: high
    requires: { energy_min: 10 }
    next: [rest, tea_break, sleep_prep, scrolling, chat_online]
  - id: sleep
    display: "睡觉"
    intensity: none
    duration: { min: 300m, typ: 450m, max: 600m }
    time_window: ["22:30-02:00"]                     # 入睡合法窗
    locations: [家/床]
    interruptible: none                               # 唯一例外：紧急事件白名单
    locks: [reply, proactive, activity_change]
    next: [wake_routine]                              # 只能醒，且醒只能去晨间流程
  ...
```

#### 2.4.3 活动转移图（Transition Graph）——合法转移的白名单

「跑步→睡觉」非法，不是写在 prompt 里求模型遵守，而是**图里没有这条边**。转移图 = 活动库 `next` 字段的并集，guard 做的存在性检查就是查边。边表节选（完整表见附录 B）：

```
running   → stretch │ shower │ snack │ walk │ rest │ chat_online     （必须先收尾/洗漱，不能直接睡）
shower    → dressing │ rest │ skincare │ sleep_prep │ snack
sleep_prep → sleep    （仅当 location=家/床 ∧ time∈入睡窗 ∧ sleep 锚点临近）
sleep     → wake_routine （仅 wake 锚点或紧急事件触发）
wake_routine → breakfast │ wash │ light_scroll │ morning_stretch
coding    → rest │ tea_break │ lunch(窗内) │ walk │ meeting │ sleep_prep(夜)
lunch     → rest │ nap(窗内) │ coding │ walk │ chat_online
任何活动  → paused_<原活动>（中断挂起态，恢复时回去）
```

**图无环约束 + 时间窗约束 + 能量门控**三者叠加后，「秒睡」「瞬移」「深夜跑步」这类错乱在结构上不可能发生。

#### 2.4.4 位置图与通勤——「瞬移」也是错乱

位置是独立小图，换位置必须插入通勤活动（无事件时可被快进压缩，但事件日志里必须存在）：

```
家{床,书桌,厨房,浴室,客厅} ──walk 10m── 楼下公园
家 ──metro 35m── 公司 ──walk 5m── 咖啡馆
```
guard 校验规则：位置变更 diff 中 `elapsed ≥ travel_time(边)`，否则拒绝。

#### 2.4.5 动力学函数——疲劳/情绪/社交电量的确定性演化（每 tick，无 LLM）

```python
# dynamics.py —— 全部确定性，参数在 config/dynamics.yaml，可调
def step(s: WorldState, tick_events) -> WorldState:
    # ① 能量（37 的「疲劳程度」）
    if s.body.sleep_state == "asleep":
        s.body.energy = min(100, s.body.energy + 1.05)          # 睡觉回充 ~8h 满
    else:
        drain = DRAIN[s.current.activity.intensity]             # light=0.3 / medium=0.8 / high=1.6 / extreme=2.5（每 tick）
        drain += 0.15 if s.mind.stress > 60 else 0              # 压力附加消耗
        s.body.energy = max(0, s.body.energy - drain)
    # 饮食锚点瞬间 +12；咖啡休息 +5（每日上限 3 次，防滥用）

    # ② 心情：向性格基线回归 + 事件冲量
    s.mind.valence += (BASE.VALENCE - s.mind.valence) * 0.05    # 每拍回归 5%
    s.mind.arousal += (BASE.AROUSAL - s.mind.arousal) * 0.05
    for ev in tick_events:                                       # 例：被@愉快聊天+0.2；被无视-0.1；下雨-0.05
        s.mood.apply(ev.impulse)
    s.mood.label = QUADRANT[(sign(v), sign(a))]                  # 象限→标签映射表

    # ③ 社交电量：群消息密度消耗，独处回升
    s.social.battery = clamp(s.social.battery
        - 0.25 * msgs_in_tick - (0.5 if involved_in_reply else 0) + (0.8 if alone else 0))

    # ④ 饥饿（风味）：+0.8/tick，餐点锚点重置为 10
    # ⑤ 硬门控（写回前由 guard 复核）：
    #    energy<15 → 禁止开启 intensity≥medium 的新活动
    #    energy<8  → 强制转入 rest/低强度
    #    energy<3 ∧ circadian=night → 强制 sleep_prep→sleep 快进
    #    social.battery<20 → 潜水模式（不冒泡，被动回复变短）
    return s
```

数值校准：高强度 40 分钟跑步 = 8 tick × 1.6 ≈ 耗能 13；一个高强度工作日累计耗能 70–85，晚上自然处于低能量区间——**「晚上没力气只想躺平」是算出来的，不是演出来的**。

#### 2.4.6 日计划引擎——「当天状态」的剧本（但剧本服从规则）

- **06:45 日拍**：输入 = 周模板 + 当日天气 + 昨日未完成事项 + `wants` + special_day → LLM 生成当日块序列（JSON，受 schema 约束）；
- **校验器**逐块检查：每块的活动必须在活动库中、time_window 合法、锚点不被覆盖（可交换顺序不可删除 hard 锚）、时长在 min/max 内、能量预算可行（按动力学预估）。**不合法块自动回退为该时段的模板默认活动**，校验报告落盘；
- 计划存 `state/plans/2026-10-25.yaml`，tick 引擎逐块执行。**计划是意图，规则是执行**：被消息打断了 40 分钟 → 允许漂移，下个锚点自动回归（re-anchor，guard 补路径）；
- 由此，「当天状态设定」这个 37 担心「不能随意」的东西，变成：**LLM 提议（随意性来源）→ 规则校验（合逻辑保证）→ 锚点兜底（结构下限）** 三层防线。

### 2.5 事件驱动打断（Interrupt）——消息如何扰动状态

快拍只做两件事：入队 + 计数。真正的打断决策在 tick 或 P0 即时通道里，按**可中断性 × 消息强度**矩阵执行：

| 活动 interruptible \ 消息级别 | P0（私聊/被@/回复我） | P1（点名未@/热议相关） | P2（普通群消息） |
|---|---|---|---|
| **high**（看书/刷手机/闲聊） | 立即响应，活动 `paused` | 下一拍响应 | 只更新密度计数 |
| **medium**（跑步/游戏/通勤） | 延迟 2–10min 响应（「等下，跑完这圈」），活动照常 | 活动结束后浏览，可补一句 | 只计数 |
| **low**（洗澡/小憩/专注块） | 挂起至活动结束（≤45min 窗口），结束后优先处理 | 挂起 | 只计数 |
| **none/asleep**（睡眠） | **紧急词白名单**（「急」「出事」「帮」等，可配置）→ 唤醒；否则静默，**次日晨间 catch-up** 补看补回 | 静默 | 静默 |

- 打断有代价记录：`paused` 超过该活动 max_duration 的 50% → abandon（事件记 `abandonment_reason: interrupted`，供夜间 reflect「今天老被打断，有点烦」这种情绪积累的素材）；
- 被打断的活动结束后若未恢复，guard 在下一拍提议恢复或转入 `next`。

### 2.6 连贯性守卫（CoherenceGuard）——唯一写入点

所有状态变更（无论来自规则、日程、LLM 提议还是插件）都打包成 **proposal**，统一走 guard：

```python
class CoherenceGuard:
    RULES = [
        R1_time_monotonic,        # 时间不倒流；duration ∈ [min,max]
        R2_edge_exists,           # 转移必须在转移图中有边（paused/resume/快进过渡除外）
        R3_time_window,           # 新活动在其 time_window 内
        R4_location_reachable,    # 位置变更需通勤时间 ≥ 图上边权
        R5_energy_gate,           # 能量门控（§2.4.5 ⑤）
        R6_sleep_invariant,       # asleep 期间只允许 wake 或紧急唤醒两种变更
        R7_anchor_fidelity,       # hard 锚点 ±drift 必须达成（否则触发兜底③）
        R8_single_activity,       # 同时只有一个活动；多事件进 interrupt_queue
        R9_wants_schema,          # wants ≤3 条、去重、TTL 24h
    ]

    def apply(self, state, proposal) -> (new_state, events):
        report = self.validate(state, proposal)
        if report.ok:
            return self.commit(state, proposal)               # 事件入 log（带 reason）
        # 兜底策略（按序尝试）：
        # ① 修正：proposal 非法但可修（如时长超限→截断到 max）→ 修正后提交
        # ② 替换：非法且不可修 → 用该时段模板默认活动替换，拒绝原因入 log
        #   （LLM 提议被拒率是核心监控指标：持续 >5% 说明活动库需要扩充）
        # ③ 补路：锚点到期但当前活动无法直接转移（如 00:30 sleep 锚点到了，
        #   还在 running）→ 在转移图上 BFS 求最短合法路径（running→walk→rest→
        #   sleep_prep→sleep），以「快进」方式压缩执行（若期间无 QQ 事件，
        #   整段压缩为一条事件；有事件则在该点展开为真实时间线）
        return self.fallback(state, proposal, report)
```

**这就是反例「上一轮在跑步，下一轮在睡觉」的命运**：R2 查边 → `running→sleep` 无边 → 兜底②替换/兜底③补路，二者都保证日志里出现完整的因果链（哪怕被压缩）。系统里**不存在**任何一条能绕过 guard 的状态写入路径，包括 LLM、插件、手动调试接口（调试也走 proposal，reason=admin）。

### 2.7 心跳状态如何注入对话上下文（三层上下文 + 风格调制）

**上下文组装（context assembler，每次回复前执行）：**

```
┌ system ──────────────────────────────────────────────────────┐
│ [人格层·静态] 身份/性格摘要（MVP: 模板；M5+: 从 knowledge bank 渲染）│
│ [硬规则] 群规禁忌、作息自述（"我一般 00:30 睡 8 点起"）          │
│ [状态层·动态] ←心跳渲染器（模板渲染，0 LLM 成本）               │
│ [记忆层] ←recall 结果（§3.3，每条 ≤60 字）                     │
├ history ────────────────────────────────────────────────────┤
│ 本会话最近 12 轮（burst 已合并）                              │
├ user ───────────────────────────────────────────────────────┤
```

**状态渲染器输出示例（由 WorldState 模板直出，喂给 LLM 的就是这样一段人话）：**

> 【当前状态 2026-10-25 周六 22:15｜夜｜多云 22℃】我在家书桌前看书（《三体III》最后两章，21:40 开始，预计 22:30 结束）。精力 38/100，有点累了；心情惬意但不兴奋；社交电量 45。我想要：想喝点热的、想把这本书看完。接下来打算看完就洗漱睡觉。
> 【最近的变化】21:40 刷完手机开始看书｜21:05 洗完澡｜20:10 吃完晚饭散了会步

**风格调制表（写进 system prompt 的行为规则，由状态数值驱动）：**

| 状态条件 | 对回复的调制 |
|---|---|
| energy < 25 | 回复 ≤2 句，少 emoji，可以直说「困了」「明天聊」 |
| arousal > 0.5 | 感叹号/emoji 上调，句子变短频 |
| valence < -0.3 | 语气平淡收敛，回避热闹话题 |
| social.battery < 20 | 潜水模式：只被@时简短回应 |
| activity.interruptible=medium 且未暂停 | 可以说「等下，我在跑步」先短回 |
| sleep_state=asleep | **不回复**（§2.5 白名单例外）；次晨 catch-up 时自然解释「昨晚睡得早」 |

**关键效果**：被问到「你在干嘛」时，Agent 的回答来自状态机事实（渲染层可加 1 次轻量 LLM 润色），**前后两小时被问两次，答案一定连续**——因为答案的源头是同一个 WorldState 的演化，而不是模型的即兴发挥。

### 2.8 反例走查：周六傍晚那次差点发生的「跑步→睡觉」

时间线（周六）：18:50 跑步（周六 morning_run 改傍晚场景）→ 19:35 跑完 45 分钟 → 19:36 tick：

1. 计划块到期，planner 提议下一块 = `sleep`（LLM 当天计划生成时手滑把休息写成了早睡）；
2. guard：R2 查边 `running→sleep` ❌ 无边；R3 睡觉 time_window 22:30 前也 ❌；R5 energy=58 未到强制睡 ❌；
3. 兜底②：替换为该时段模板默认 `rest`，拒绝原因 `llm_proposal_rejected:edge_missing` 入 log（并计入 LLM 提议拒绝率监控）；
4. 19:40 挂起 rest 收到 P0 消息 → 正常回复「刚跑完步在缓一缓」（事实来自状态：刚从 running 转入 rest）；
5. 23:05 wind_down 锚点 → sleep_prep（有边）→ 00:31 sleep（有边+窗内+位置床上）✅。

**全程没有出现任何一次非法状态，且每一步都有事件日志可查。**

### 2.9 心跳 ↔ Hindsight 联动（retain 的节流阀）

- **值得记才 retain**：每 tick 的差值过滤——只有「块切换/锚点/被打断/情绪冲量 ≥0.2/播报发出」这类事件才进 retain 队列，文本化如 `19:36 周六，我结束了 45 分钟跑步，有点累但挺爽`。一天心跳事件 retain 约 10–20 条（而非 288 条）；
- 长期作息/情绪规律（「37 周末晚上习惯安静」「我周六爱跑步」）由 Hindsight Observations 后台自动固化——**心跳系统给 retain 提供天然节流**（按拍批量，token 成本可控，《接入评估》1.4 结论的直接落地）；
- disposition traits（bank 级配置）+ Opinion 网络 = 性格底色与「我对每个群友的看法」，与心跳 mood 互不越界。

### 2.10 事件溯源、回放与压缩测试（工程保险）

- `state/events.db`（SQLite WAL）：append-only 事件表 `(ts, from, to, reason, meta, version)`；`replay.py` 可从零重建任意时刻 WorldState；
- **虚拟时钟注入**：引擎所有时间读 `clock.now()`，测试模式注入快进时钟 → **10 分钟压缩跑完 72h**（含全部 tick/锚点/转移），断言「零非法转移 + 零孤儿活动」——M2 验收就靠它，不用真等三天；
- 每日 00:10 导出 `state/snapshots/YYYY-MM-DD.yaml` + `git commit`（进 vault 仓库），状态演化全程可 diff。

### 3.1 双 bank 拓扑

| bank | 内容 | 写入者 | 检索者 |
|---|---|---|---|
| **qq-agent** | 对话记忆（retain 摘要）+ 心跳事件 + reflect 产物 → Experience/Observation/Opinion | console（REST） | console（recall/reflect） |

### 3.2 retain：触发时机与数据流

| 触发 | 条件 | payload |
|---|---|---|
| 会话尾批 | 会话 idle 8 分钟（无新消息） | 该会话自上次 retain 后的轮次摘要（见下） |
| 心拍批 | 心跳事件队列非空且距上批 ≥30min | 心跳事件文本（§2.9 过滤后） |
| 即时 | 单轮重要度 ≥2（LLM 回复时自评 0–3，工具调用附带返回） | 立即单条 |
| 日终汇总 | 02:00 reflect 前置 | 当日 plans + 播报 + 会话统计（供 reflect 全景） |

**对话摘要格式（控制 token，事实密度优先）：**

```

```

```json
POST /v1/memory/retain   （console → Hindsight）
{ "bank": "qq-agent",
  "content": "<上文本>",
  "metadata": { "chat_id": "G123", "user_ids": ["37"], "kind": "dialogue",
```

**成本控制三闸**：重要度过滤（0–1 级且超当日预算→丢弃）、心拍节流（§2.9）、provider 用 DeepSeek（抽取/embedding 便宜；M4 后视质量决定是否开本地重排器）。

### 3.3 recall：回复前的记忆注入

- **触发**：每次 P0/P1 回复生成前（P2 观察不触发）；
- **query 构造**：`话题关键词(近 3 轮) + 提问者档案键 + 状态摘要(≤40字)`，如「minecraft 整合包 37 的偏好 周六晚上」；
- **过滤**：metadata `chat_id` 或 `user_ids` 命中优先；单群部署先不做 per-user bank，用 metadata 过滤模式（官方两种隔离模式之一）；
- **注入**：top_k=8、总预算 ≤600 token，每条压成 `- (10-22) 37 喜欢轻量整合包，之前聊过 FamilyPack`；
- **降级**：recall 超时 800ms 或服务不可用 → 跳过记忆层照常回答（对话永不因记忆层故障而中断）。

### 3.4 reflect：两个触发场景

| 场景 | 触发 | 数据流 |
|---|---|---|
| **深水问答** | 用户问题被分类为「需要深度回忆/观点」类（路由规则：含「你还记得/你怎么看/为什么」且涉过往） | query + 近期 Experience → reflect（CARA，带行为画像）→ 生成带观点的回答，同时新观点写回 Opinion 网络 |
| **夜间反思** | 每日 02:00（Agent 睡着时——「做梦」即后设整理） | 日终汇总（§3.2）→ reflect → 巩固当日 Observations（去重、合并证据、refined-not-overwritten） |

监听 Hindsight webhook 的 `consolidation`/`refresh` 事件 → 使能知识页缓存/通知 vault 投影刷新。

### 3.5 traits/state 分工（与心跳的接口）

- bank 级 **disposition traits**（怀疑度/字面度/共情度）在创建 bank 时设定 + 周拍微调（人确认）→ 影响对话语气底色；
- **心跳 mood** 只管当日瞬时波动 → 影响本轮回复风格（§2.7 调制表）；
- **Opinion 网络** 管「我对 37 的看法」这类信念演化 → 长期关系质感。三层各管一段，互不覆盖。

**五条红线（写死进部署 checklist）**：a) 每方向单源单向；b) 一个 vault 一个 ingest 通道；c) 投影目录只读心智；d) 对话记忆与 vault 知识分 bank；e) 服务器自托管 + Memory Defense 开启。

**生效闭环验收**：改 `knowledge/persona.md` 一条设定 → ≤15min 同步 → recall 能答出 → Agent 行为可观测变化（M5 验收项）。

### 3.7 隐私与边界

- Memory Defense 开启（45 种密钥/PII 模式，改写为 `[REDACTED]`）——QQ 群聊天入库的最后保险丝；

### 4.2 优先级仲裁（消息 vs 心跳 vs 播报）

**事件分级表：**

| 级别 | 事件 | 时效要求 | 可抢占/可丢弃 |
|---|---|---|---|
| **P0** | 私聊；群里被@/被回复；紧急唤醒词 | 立即（目标延迟 ≤3s 起算） | 抢占在途 P1/P3 生成（取消其 LLM 请求） |
| **P1** | 群内点名（含名字未@）/与当前话题强相关的热议 | 下一拍内 | 可被 P0 抢占；节流丢弃 |
| **P2 观察流** | 其余全部群消息 | 无 | **永不触发 LLM**，只更新密度/注意力（风控与成本的第一道闸） |
| **P2 心跳 tick** | 5min 节拍 | 30s 内完成即可 | 与 P0 错峰：tick 在有 P0 队列时让出 |
| **P3 主动播报** | 心跳产生的冒泡提案 | 分钟级 | **可丢弃**（配额满/静默时段/连续丢弃计数） |
| **P3 插件后台** | 天气拉取、vault 同步触发、提醒到期 | 分钟级 | 可延迟 |
| **P4 维护** | 夜间 reflect、快照、git、备份 | 固定凌晨窗口 | 不可抢占 P0-P3（反正凌晨没流量） |

**仲裁规则：**
1. LLM 并发 = 1（人格一致性 + 成本）；队列按优先级 FIFO，P0 插队头部；
2. **burst 合并**：同一 sender 连续消息，400ms 窗口滚动合并（每条新消息重置计时器，上限 8 条/2.5s 防粘连）→ 一次生成回复；
3. **回复限流**：单群 ≤8 条/分钟（令牌桶），超限排队并触发 LLM 合并多问多答为一条；
4. **睡眠门控**：`sleep_state=asleep` 时 P0 先过紧急词过滤器，非紧急直接进「晨间 catch-up 队列」（次晨统一 recall 摘要处理）；
5. **重复抑制**：相同语义提问 3min 内命中缓存直接复用变体回复。

### 4.3 对话管道（P0 完整路径）

```
gateway.at_me? → sessions.merge_burst(400ms) → arbiter.P0
 → heartbeat.snapshot() + memory.recall(query) + persona/rules
 → context.render()（§2.7 三层） → llm.chat(tools=plugin_manifests)
 → [tool_call? → plugins.route → result → llm 二轮]（≤2 轮）
 → outbound.shape(分条/延迟/配额) → gateway.send_group_msg
 → sessions.append + importance 标记 → retain 队列（§3.2 节流）
```

### 4.4 插件技能框架

**manifest（`plugins/<name>/skill.yaml`）+ 注册/发现/调用：**

```yaml
name: weather
version: "1.0"
type: passive            # passive=LLM 工具 | active=心跳条件触发 | 两者可共存
description: 查询指定城市当前/24h/3天天气     # 进 LLM 工具列表的就是这句
tool:
  function: get_weather
  parameters: { city: {type: string}, range: {enum: [current, hourly24, daily3]} }
  timeout_s: 10
permissions: [net:https://api.open-meteo.com]   # 网络出域白名单，运行时强制
active:
  every: 30m
  condition: "weather.condition in [rain, snow] and current.activity.outdoor"
  action: propose_broadcast("下雨了，我得收衣服/躲雨")   # 仍走 P3 配额，不豁免
entry: main.py            # asyncio 子进程执行，stdin/stdout JSON
```

- **发现**：启动扫描 `plugins/*/skill.yaml` + SIGHUP 热重载；manifest 校验（pydantic schema）；
- **调用（passive）**：LLM function calling → router 查表 → 子进程执行（超时 kill，错误以「工具暂时不可用」回给 LLM 触发降级话术）→ 结果回填继续生成；
- **调用（active）**：每 `every` 评估 `condition`（只读 WorldState + 插件自拉数据）→ 命中则产出播报提案进 P3 队列，**不绕过整形**；
- **沙箱**：子进程无 console 内部状态写权；文件系统只读自己目录 + tmp；网络按 permissions 白名单；QQ 发送只能走 outbound（保持拟人整形统一收口）。

## 5. 通道层：SnowLuma + OneBot v11

### 5.1 部署拓扑（二选一）

| 拓扑 | 形态 | 适用 | 备注 |
|---|---|---|---|
| **A（推荐）** | Windows 小主机/旧笔记本：QQ 客户端 + SnowLuma 完整包（`launcher.bat`，WebUI :5099）；其余组件在 Linux 服务器 Docker | 长期跑 | hook 稳定性最好、扫码登录方便、独立设备隔离风控（NapCat 安全文档建议 Bot 号不与常用号同 IP/设备） |
| B | 全 Docker：SnowLuma.Docker.Framework（LinuxQQ + Xvfb + VNC/noVNC + supervisord，官方自家方案）与 console 同 compose | 无 Windows 机器 | 登录走 noVNC 扫码；LinuxQQ 资源 ~1.5–2GB |

两种拓扑下 console 与 SnowLuma 均走**反向 WS**（SnowLuma 主动连 console 的 :8080/onebot，accessToken 鉴权）——console 是频繁迭代重部署的一侧，让长跑的 SnowLuma 反向重连，恢复语义最简单。**切换位**：契约是 OneBot v11，SnowLuma 出问题可平替 NapCat/LLOneBot（反向 WS 同为标配），console 零改动。

### 5.2 OneBot v11 契约（用到的事件与动作）

| 类别 | 条目 | 用途 |
|---|---|---|
| 订阅事件 | `message.group` / `message.private` | 主消息流（P0/P1/P2 分级入口） |
| | `notice.notify.poke`（戳一戳） | 玩耍性互动（qq_actions 插件） |
| | `notice.group_increase` | 新人欢迎（低频、走配额） |
| | `meta_event.lifecycle` / `meta_event.heartbeat` | **连接活性 + hook 健康监控**（见 5.5④） |
| 调用动作 | `send_group_msg` / `send_private_msg` | 发消息 |
| | `get_group_member_info` / `get_login_info` | 名片昵称解析（@显示名↔QQ 号映射） |
| | `send_poke`（如实现支持） | 戳回去 |
| | `set_group_whole_ban` 等管理类 | **默认禁用**（白名单动作表外一律拒绝） |

消息体以 **array 段格式解析**（`reply/at/image/record` 段），CQ 码字符串兜底转换；@解析出 `at_me`；媒体先落盘对象存储目录（`data/media/`）再交给 LLM（多模态留 M6+，MVP 只登记「发了张图」事实）。

### 5.3 收发细节

- **收**：事件 → envelope`(chat_id, sender, segments, at_me, reply_to, ts, raw)` → bus；
- **发**：`send_group_msg(group_id, message=[{type:reply,...},{type:at,...},{type:text,text:...}])`，分段由 outbound 决定（多条消息间 1–3s 间隔模拟打字）；
- accessToken 全链路（SnowLuma 出口配置 + console 服务端校验）；QQ 与 console 不在同一网络时走 wireguard/Tailscale（自托管，不开公网端口）。

### 5.4 主动播报管道（心跳→QQ 主动消息）

```
heartbeat tick 产生播报提案(P3)
 → 条件：块切换且 share_value≥阈值 / 锚点事件 / wants 冒泡冲动(p=0.15×心情因子)/天气事件
 → 配额闸：日 ≤8 条、小时 ≤2 条、最小间隔 25min、静默 00:00–08:00（asleep 天然静默）
 → LLM 生成文本（带状态渲染，语气随 mood）→ outbound 整形：
     随机延迟 20s–4min（泊松）→ 长文拆 1–3 条 → 发送
 → 事件 retain（"22:30 我在群里冒泡说了看书看到结局了"）
```

share_value 由活动库字段 `share_worth`（0–10）× mood 因子决定：「跑步遇到猫」>「又一次刷手机」。**拟人化整形是风控第一道闸**（《通道层调研》4.2 风险#1 缓解项的行为落地）。

### 5.5 风控应对手册（自托管个人号的结构性风险，只能管理不能消除）

1. **账号隔离**：专用小号；独立设备/独立 IP（不与 37 常用号同环境）；不绑常用支付/密保；
2. **版本锁定**：QQ 客户端锁定已验证组合，跟随 SnowLuma/NapCat 社区节奏灰度升级（2026-03 NTQQ 3.2.25 触发踢线、社区锁 3.2.23 先例——《通道层调研》2.3）；
3. **登录熔断**：守护脚本连续登录失败 3 次即停机告警等人扫码（连续快速重登会触发临时冻结——实战复盘结论）；`o3Hook=0` 关包拦截；异常网络配 SOCKS5（NapCat 安全文档同源经验）；
4. **hook 静默退化监控**：不只看端口/online——监听 `meta_event.heartbeat` 的 `status.good` + 消息流 watchdog（30min 零事件且群已知活跃 → 告警 + 自动重启链路）；`get_status.online` 是「假在线」不可信；
5. **行为整形**：§5.4 配额 + 回复延迟抖动 + 人类活跃时段分布（作息引擎天然提供：深夜本来就不说话）；
6. **备份通道（可选，M6+）**：官方龙虾 Bot + 官方 Agent 插件作通知/广播冗余（合规零风险，但限额群 1000 条/日、被动回复 5min5 次，只能当备份，不能承载心跳式互动——《通道层调研》三的结论）。

### 5.6 SnowLuma 许可红线

- 非商业自托管**免费**【OK】；**不要**把包含 SnowLuma 的整合包/镜像公开分发（源码可见非商业许可 + EULA §5.4 自动化部署分发限制）——本方案的交付物里 SnowLuma 永远是「用户自行安装的外部依赖」，compose 里只留配置模板与安装文档；
- 一旦将来商业化 → 书面授权或切 NapCat/LLOneBot（OneBot v11 契约不动，console 无感）。

## 6. 技术选型

| 项 | 选型 | 理由 | 备选 |
|---|---|---|---|
| console 语言 | Python 3.11 + asyncio | Hindsight 官方 Python SDK 同语言；aiocqhttp/websockets 生态成熟；pydantic v2 做状态模型 | Node/TS（@snowluma/sdk 原生，若团队 TS 熟可换，架构不变） |
| WS 服务端 | websockets（反向 WS server） | 轻量、可控重连语义 | aiocqhttp |
| LLM（对话/提议） | DeepSeek（OpenAI 兼容 API） | 成本低、中文强；JSON mode 支持结构化提议 | 任何 OpenAI 兼容端点（含本地 vLLM） |
| Hindsight provider | LLM=DeepSeek；embedding 同；reranker M4 前关闭 | 25+ provider 官方支持；关重排省 ~3.5GB 内存（recall 50–100ms 够用） | ollama 全本地（bge-m3+GGUF 重排） |
| 状态存储 | SQLite WAL + 每日 YAML 快照 + git | 事件溯源天然 append-only；YAML 人类可审计 | PostgreSQL（规模大了再换） |
| 天气 | Open-Meteo | 免 key、商用友好 | 任何天气 API |
| 语音（M6+） | Fish Audio s2.1-pro-free | 免费窗口至 2026-11-30、模型不阉割（《Fish-Audio 调研》结论） | edge-tts 兜底（哨兵建议保留迁移位） |
| 配置 | YAML + .env（密钥） | 人格/作息对 37 可读可改 | — |
| 日志/监控 | structlog JSON + 每日日报进 vault + uptime-kuma（可选） | 审计与告警最低成本闭环 | — |

**成本估算［粗估，以当期牌价为准］**：活跃群（日 200 条消息，其中触发回复 ~30 轮）+ 心跳 retain + 夜间 reflect ≈ 15–20 万 token/日 → DeepSeek 计**单日 ¥0.1–0.3 量级**；基础设施 0 元（自托管）。Hindsight reranker 关闭时整机内存占用：Hindsight ~4GB + console ~0.3GB + SnowLuma(Docker) ~2GB → **8GB 机器可跑，16GB 舒适**。

| 4 | 记忆 token 成本失控 | 中 | §3.2 三闸（重要度/节拍/DeepSeek）；reranker 默认关 |
